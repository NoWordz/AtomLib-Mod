# 前端契约锁方案审计

日期：2026-11-17。审计对象：docs/superpowers/plans/2026-11-17-v060-frontend-contract-lock.md 第一版，300 行。

正式名称已经由用户确认为“前端契约锁”。本轮只做方案审计和只读源码核对，不修改原方案正文、实现、版本或测试，不执行技术探针。

## 结论

已确认的 D01—D20 没有发现需要推翻的直接冲突。当前稿有 **4 项在功能实现前需要补齐的机制缺口，另有 5 项契约或验收定义遗漏**。可以保留总体方向，但不能把本稿当成所有关键机制已经确定的实施规格。

这里的“阻断”指不宜直接进入功能实现；不否定方案先做窄原型、遇到不可行时回到设计的顺序。第 13 节主动列出的待核实事项不是缺陷本身；本报告指出的是这些事项目前对应哪些尚未兑现的保证，以及至少应补到什么程度。

本次为主代理静态审计与源码核对，没有运行验证器、编译或游戏。以下反例是方案当前允许的实现风险，不冒充已经复现的 0.6.0 程序缺陷。

## R1 阻断：消费者获得 JAR，不等于获得 CI 约束

**位置：** 方案第 9 节工具安排、第 10 节阶段三至四，尤其第 197、236、241 行。

方案把检测器放在 tools/frontend-contract-lock/，同时要求真实消费者从分发依赖接入。但未定义检测器作为何种可获取制品交付、消费者怎样安装、接到哪些标准任务、检测器与契约格式如何匹配。

现有 settings.gradle 只包含 core、runtime、ui 和 probes:yoga；gradle/module-layout.gradle 将三个公共模块类与资源合入平台 JAR，tools/package_maven_input.py 只归档已有 Maven 输出。现有机制不会因为新增一个 tools 目录，就把检查器安装到消费者构建里。

**失败路径：** AtomChat 本机通过仓库相对路径调用扫描器，Lib 自身 CI 全绿；另一个项目只安装正式 JAR，普通 build 并未运行扫描器，却按照文档以为已经启用前端锁。

**修订要求：** 将“可分发的构建检查接入物”列为正式交付物，明确获取方式、版本协商、Gradle 标准任务接线、非正常退出传播和缺接线诊断。具体用插件还是独立检查器由最小探针决定，不要求先引入新工具链。增加干净消费者负例：仅使用分发制品、没有 AtomLib 源码目录，合法页面通过，越权页面导致标准验收任务失败；遗漏接线不能被报告为已启用且通过。

阶段三的“实际发布依赖”应明确为可分发候选制品，不能解释成必须先公开发布 0.6.0 才能验证消费者。

## R2 阻断：旧页面豁免可能吞掉所有新页面

**位置：** 第 27、104、156—158 行。

方案同时保留自由入口、允许既有页面暂不迁移，并要求所有新增页面和组件必须受锁。但是“可枚举入口”从哪里穷举、旧豁免的最小单位是什么，尚未定义。

AtomChat 的 Fabric AtomChatScreen 中，PageTransitionComposite.Host 按 AppPage 分派 body、header 与 bodyVariant；大量页面与外层绘制共用一个 Screen。新增界面不必产生新的 Screen 或页面类，也可以只在现有路由中增加分支、在现有方法里画一块内容。

**失败路径：** 将整个旧 Screen、目录或文件标为未迁移，随后在其中添加新路由或绘制分支。新内容没有进入严格页面工厂，扫描器也没有“未知入口”可检查，因而从未报红。

**修订要求：** 明确首版支持的宿主和源码语言、完整的 UI 接入点集合、旧豁免的登记单位，以及新增或修改接入点的识别规则。豁免不能按目录或可任意增补内容的整个文件无限扩张。宿主路由、HUD、模态和外层装饰各自标明覆盖边界；不能通过只锁 body 而把新美术画到 header 或 overlay 里逃逸。

必须增加“在已有文件和已有路由中新增未登记界面”的负例，以及“正常保留的旧页面仍可工作”的正例。做不到某种宿主入口的可靠覆盖时，应明确首版不支持该入口，而非泛称项目全部新增 UI 已受锁。

## R3 阻断：批准流程有原则，但缺少可执行的版本选择协议

**位置：** 第 110、142—148、290 行。

方案正确区分了候选合规与已获批准，也明确不做权限沙箱。但是还没有规定普通检查从哪里取得已批准版本、当前变更能否改变这个选择、设计候选运行后会返回什么状态，以及批准影响哪些定义和消费者。

**失败路径：** 定义、实现、基准和“所使用的设计版本”在同一批变更中被一起更新。检查器按工作树中的新版本运行，全绿。报告写着“设计变更”，但普通页面仍能消费它，批准顺序并未真正约束构建。

**修订要求：** 定义普通页面模式与设计候选模式，并区分“已批准且合规”“候选验证通过但待设计审查”“不合规”。普通模式的已审定设计来源必须明确，变更该来源也属于需审查的配置变化。候选模式不能把结果发布为普通页面已获批准。

用常规项目设计版本、变更差异和所有者审查即可，不需要 SHA 信任副本或只读锁。批准范围应明确到族群／配方及其依赖变化；新增页面不能靠把基准引用改成当前工作树就自行晋级。

## R4 阻断：只固定设计参数，不能保证升级库后风格稳定

**位置：** D14，以及第 126、136 行。

方案要求库机制升级与设计升级分开，却没有定义一个设计版本是否包含布局解释、材质算法、动画曲线和状态优先级。只固定 palette、MotionSpec 参数或族群 ID，不能兑现这个保证。

现有 SettingsRows.feedback 中，高亮透明度系数直接写在绘制实现；ThemeSnapshot 的选区透明度等派生规则也在代码中；Control.advance / approach 和 MotionSpec.scale 决定时间与反馈的解释方式。这些函数被新版库改动时，输入参数和族群 ID 完全不变，外观或手感仍然会改变。

**修订要求：** 明确设计版本包含哪些可观察语义，以及其对应的兼容解释实现。共享渲染资源与后端可以改进，但不能静默替换旧设计的曲线、布局或材质规则。库升级要用旧设计版本运行回归；若无法保留某个版本的表现，必须明确要求设计迁移，不能把它当成普通机制升级。

不要求冻结全部库代码或为每个版本复制一份框架；要求的是可检验的兼容边界。

## R5 遗漏：Java 类型化声明不天然等于确定性设计数据

**位置：** 第 108—110 行。

Java 声明仍然可以读取环境、时间、系统属性或调用任意函数。当前文字没有说明设计注册表是由构建清单固定，还是会在运行时再次执行设计声明。只读句柄也只能限制后续写入，不能保证句柄最初指向了同一份内容。

**失败路径：** 构建时生成报告使用一种参数，游戏启动时重新执行声明得到另一种参数；两者沿用同一个 ID 和版本。截图基准与注册表都存在，但审查对象与运行对象不同。

**修订要求：** Java 可以保留为作者编写形式，但应规定哪些输入允许参与解析，并形成一次确定的、不可变的设计描述。运行时消费同一份解析结果或经验证等价的结果，变化只能来自契约声明的参数入口和命名条件。禁止设计声明暗中捕获环境或任意运行时回调作为视觉定义。

增加“同一设计版本在不同构建／运行环境得到未声明差异”的负例，以及“明确定义的主题参数变化合法”的正例。

## R6 遗漏：条件触发可能把必需行为变成永远不会执行

**位置：** 第 94—104、164、176 行。

方案要求条件可判定、实际行为要验证，但没有规定条件由谁拥有、预期来自哪里、是否必须验证条件成立。设计声明和测试若共同读取同一个错误条件，仍可相互证明正确。

**失败路径：** hover 被写成条件触发，但条件恒为假；或所有测试都把交互控件设为禁用。运行时从来没有出现高亮，测试却称条件不满足、因此没有遗漏。类似问题也会出现在零时长采样、只检查动画结束帧和仅使用默认主题上。

**修订要求：** 项目获批角色基线决定哪些能力必需，配方不能自行把它们改成不可达条件。条件使用明确状态输入与语义；条件触发项要有成立和不成立的验证依据，无法到达的条件必须被报告而非计为通过。动态预期独立于候选声明，不仅检查它自己声称需要执行的分支。

补充最小覆盖矩阵：角色能力、启用／禁用、状态组合与转换、开放参数边界、适用的主题和缩放。用角色要求与实际使用确定范围，不穷举全部组合。动画要求至少验证过程中的必要变化，不能只验证首末帧相同。

## R7 遗漏：尺寸来源合法，仍可能因为单位混用而算错

**位置：** 第 118—126 行。

方案禁止页面手算并要求同源几何，但没有固定逻辑单位、Minecraft GUI 坐标、窗口坐标、设备像素和字体测量之间的换算边界。

现有 SettingsPageStyle 同时具有 uiScale 和 contentScale；SettingsShell 进一步使用 viewport.pixelsPerUnit、PresentationFrame.scaled 和输入坐标准备。实现可以全部引用合法 token，却因重复缩放或混用单位而出错。

**修订要求：** 在严格 API 前明确一套布局单位、外部输入转换边界和变换顺序。组件不得重新应用已经完成的缩放。至少覆盖不同 GUI 缩放、窗口尺寸、内容缩放和动画期间的绘制—命中一致性。数值来自 token 不能作为几何正确的替代证明。

## R8 遗漏：内容插槽能限制权限，不能识别任意图片的语义

**位置：** 第 134 行。

“不能通过业务图片伪造组件”的表述过宽。用户头像或表情包本来就可能是一张按钮、卡片或界面的截图；框架不能既允许任意业务图片，又保证这些像素不描绘 UI。

**修订要求：** 把承诺收窄为可检查的能力边界：内容只能进入声明插槽，不取得材质槽、任意绘制回调、越界层级、组件身份或额外命中区域。禁止以内容通道替换设计槽；不判断普通图片本身是否画了一个按钮，也不增加图像语义审查。

增加两类正反例：合法头像使用 UI 截图仍可显示；页面试图让同一图片占用卡片材质槽或越界铺满页面必须失败。

## R9 遗漏：真实消费者接入与实机验收的完成口径未分开

**位置：** 第 168、236、281、299 行。

方案明确离屏不代表实机，这一点正确。但同时把“完整真实两页闭环”和“用户认可观感”列为完成条件，又允许实机条件留待验证，没有明确哪部分未完成时只能称为候选。

现有 SessionConsumerProbe 证明的是对分发坐标的独立调用与部分会话行为，不运行实际 MC 页面。未来即使增加真实项目编译和离屏入口，也不能自然覆盖游戏最终合成、GUI 缩放、失焦和输入链。

**修订要求：** 区分三个状态：分发消费者可构建、生产代码的受控场景通过、真实游戏的指定流程获验收。明确 0.6.0 对试点完成至少要求哪一种状态，以及允许留存哪些环境限制。建议将已选试点的最终游戏合成与关键输入列为正式试点验收条件；未满足时交付候选和未覆盖清单，不能称该部分已经完成。

这不授权代理自行启动游戏或部署。实机步骤仍由实际授权和用户操作决定；若项目所有者另行允许带已知限制交付，需要明确记录范围，不能在方案中默认降级。

## 建议的修订顺序

1. 先补 R1—R4：明确消费者交付和接入、入口与遗留范围、批准状态协议、设计版本兼容边界。这些决定探针真正要验证的目标。
2. 合并补齐 R5—R7 的数据、条件、单位和最小场景契约，避免后续边写边改变判据。
3. 收窄 R8 的不可执行承诺，明确 R9 的候选与完成口径。
4. 将对应正反例补进原方案的阶段结果和负例表。完成一次覆盖自查即可；不要为此追加权限系统、SHA 锁或全量 UI 迁移。

上述建议保留既有 20 项产品决定。这里没有提出新的图标逐张审批、所有尺寸固定化、全状态穷举或性能族群预算要求。
